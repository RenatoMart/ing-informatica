## 0. Convenciones globales

| Tema | Decisión |
|---|---|
| Idioma del código de dominio | Español sin tildes en los identificadores (`PublicacionesServicio`, `enviarRevision`). Las clases del framework mantienen sus nombres en inglés (`Controller`, `FormRequest`, `Middleware`). |
| Tablas y columnas | Las del diccionario, en minúsculas y en singular: `rol`, `usuario`, `bitacora_acceso`, `solicitud_acceso`, `departamento`, `publicacion`, `archivo_publicacion`, `docente`, `especialidad_docente`, `consulta_contacto`, `plan_estudios`, `curso`, `prerrequisito`, `documento_oficial`, `campana_admision`, `modalidad_admision`, `cronograma_admision`, `registro_visita`. |
| Tipos | `INT` PK → `INT GENERATED BY DEFAULT AS IDENTITY`. `DATETIME` → `TIMESTAMPTZ`. `ENUM` → tipo `ENUM` de PostgreSQL con los literales exactos del diccionario (ver 4.0). |
| Zona horaria | `America/Lima`. Se fija en `config/app.php` (`'timezone' => 'America/Lima'`) y en `config/database.php` (conexión `pgsql`, `'timezone' => 'America/Lima'`), así `current_date` en PL/pgSQL es la fecha de Lima. |
| JSON | Claves en `snake_case` en español, iguales a las columnas. Fechas en ISO 8601 (`2026-10-27` o `2026-10-27T14:05:00-05:00`). Las URLs de archivos se devuelven absolutas. |
| Elementos "extra al informe" | Todo lo que no está en el diccionario se marca **[EXTRA]** y debe documentarse después en el informe del Sprint 2. |
| Secretos | Nunca se escriben en archivos versionados. `.env` y `.env.testing` están en `.gitignore`. Solo se versiona `.env.example` / `.env.testing.example`, con valores vacíos. |

## 1. Estructura N-capas en Laravel

### 1.1 Capas y reglas de dependencia

```
HTTP (app/Http)  ──►  Aplicación (app/Aplicacion)  ──►  Dominio (app/Dominio)
                                │                          ▲
                                └──►  Persistencia (app/Persistencia) ──┘
                                              │
                                              ▼
                               PostgreSQL (funciones sp_* + vistas v_*)
```

| Capa | Namespace | Puede usar | No puede usar |
|---|---|---|---|
| Presentación HTTP | `App\Http\Controllers\Api\Panel\*`, `App\Http\Controllers\Api\Publico\*`, `App\Http\Requests\*`, `App\Http\Middleware\*` | Aplicación y los objetos de Dominio que devuelve | Persistencia, `DB::` |
| Aplicación | `App\Aplicacion\<Modulo>` | Dominio, Persistencia, servicios Laravel (Mail, Storage, Http, Hash, Auth, DB::transaction) | Request/Response HTTP |
| Dominio | `App\Dominio\<Modulo>` | Solo PHP puro y otras clases de Dominio | Cualquier `Illuminate\*`, `DB`, `Carbon` (usa `DateTimeImmutable`) |
| Persistencia | `App\Persistencia\<Modulo>` | Dominio (para hidratar entidades y lanzar excepciones), `Illuminate\Support\Facades\DB` | Aplicación, HTTP |

Reglas:
- **Los controladores son finos**: validan con `FormRequest`, llaman a un único método de servicio y devuelven `response()->json(...)`. No llevan lógica.
- **Los repositorios son clases concretas** (sin interfaces). Se inyectan por el contenedor en los servicios. No se usa el patrón Repository+Interface porque las pruebas usan la BD real (sección 9).
- Una prueba de arquitectura (`tests/Unit/ArquitecturaTest.php`) recorre `app/Dominio/**/*.php` y falla si encuentra `use Illuminate` o `DB::`.
- Los servicios devuelven arreglos DTO (`array`) o entidades con `aArreglo(): array`. Los controladores no transforman nada.

### 1.2 Reparto Eloquent / `DB::` / procedimientos

**Decisión: la Persistencia usa `DB::` (Query Builder y SQL crudo), no Eloquent.** El curso pide procedimientos almacenados, y las reglas de estado y de integridad que el esquema no expresa (sección "Reglas que valida la aplicación" del informe) tienen que vivir en un único lugar transaccional.

| Operación | Mecanismo | Motivo |
|---|---|---|
| **Toda escritura** (insert/update/cambio de estado) | `SELECT * FROM sp_xxx(?, ?, …)` vía `App\Persistencia\Compartido\EjecutorProcedimientos` | Las reglas y la trazabilidad (decisión con fecha y usuario, historial, bitácora) se aplican de forma atómica en la BD, sin importar quién llame. |
| Lecturas del panel (listados con filtros y paginación) | Query Builder `DB::table(...)` sobre las tablas o vistas | Los filtros y la paginación son dinámicos, y escribirlos como función no aporta nada. |
| Lecturas públicas | `DB::table('v_publico_...')` | Las vistas filtran "solo publicado/vigente" en un solo sitio. |
| Autenticación de sesión | **Única excepción a "sin Eloquent"**: modelo `App\Persistencia\Usuarios\UsuarioAutenticable` (Eloquent, tabla `usuario`) usado solo por el guard `session` de Laravel | El guard necesita un `Authenticatable`. El modelo nunca se usa para escribir (`$guarded = ['*']`). |

La reglas se validan en **dos niveles**:
1. **Dominio (PHP)**: da errores amigables antes de llegar a la BD (422/409) y es la regla que se prueba en las pruebas unitarias.
2. **PL/pgSQL**: garantía final. Si la regla de PHP se salta, la función lanza la excepción.

La regla está escrita dos veces a propósito (defensa en profundidad). Una prueba feature (`MaquinaEstadosConsistenciaTest`) compara la tabla de transiciones de PHP con `sp_rev_transicion` en todas las combinaciones.

## 2. Máquina de estados de revisión (componente único)

### 2.1 Modelo común

Las cinco entidades revisables (publicación, docente, plan, documento y campaña) comparten las columnas `id_editor`, `id_director_revisa`, `fecha_decision` y `observaciones_revision`. El componente añade:

1. **Una sola tabla de transiciones** (2.2) implementada en `Dominio\Revision\MaquinaEstadosRevision` y espejada en `sp_rev_transicion`.
2. **Una sola operación de decisión**: `POST /api/panel/revision/{entidad}/{id}/decidir` → `RevisionServicio::decidir` → `sp_<entidad>_decidir(p_id_revisor, p_id, p_decision, p_observaciones[, p_como_vigente])`.
3. **Trazabilidad completa** [EXTRA]: la tabla `historial_revision` guarda **cada** transición. Las columnas del diccionario guardan solo la última decisión, y una aprobación tras un rechazo borraría el rechazo. Todas las funciones de transición llaman a `sp_rev_registrar_historial`.
4. **Cambios y bajas sobre contenido ya publicado** [EXTRA] (solo para publicación y docente, que siguen visibles mientras se revisa el cambio): columnas `operacion_pendiente VARCHAR(10) NULL CHECK IN ('cambio','baja')` y `cambios_pendientes JSONB NULL`. El registro público no cambia hasta que el Director aprueba.
5. **Regla de separación**: `id_director_revisa ≠ id_editor` (y ≠ al editor del cambio pendiente, que se guarda en `cambios_pendientes->>'_id_editor'`). Las observaciones son obligatorias si la decisión no es aprobar.

Para plan, documento y campaña, **corregir lo publicado = crear una versión nueva** (duplicar o reemplazar), que al aprobarse pasa la anterior a histórico o archivada. No usan `operacion_pendiente`.

### 2.2 Tabla de transiciones (fuente única; PHP y SQL deben coincidir)

`(op)` = valor de `operacion_pendiente`. "—" = sin operación pendiente. Actor: E = Editor (o Revisor actuando como editor), R = Revisor, S = sistema (tarea programada).

**Publicación** (`borrador, en_revision, publicada, descartada, despublicada`)
| Desde | Acción | Actor | Hacia | Efecto adicional |
|---|---|---|---|---|
| (nuevo) | guardar | E | borrador | `fecha_creacion = now()` |
| borrador | guardar | E | borrador | |
| borrador | enviar_revision | E | en_revision | notifica a los revisores |

**Publicación programada**: no se usa temporizador. Al aprobar, el estado pasa a `publicada` y la vista pública filtra `COALESCE(fecha_publicacion_programada, fecha_decision::date) <= current_date`. Así se cumple el temporizador de P2 sin tarea programada.

**Docente** (`borrador, en_revision, publicado, inactivo`): igual que la publicación, con estas diferencias: no tiene `descartar` (el Director solo puede `observar` → borrador), aprobar una baja deja el docente en `inactivo`, y existe `reactivar` (E): `inactivo → borrador`.

| (nuevo) | guardar | E | en_revision | se puede indicar `id_version_anterior` |

## 3. Autenticación y autorización

### 3.1 Mecanismo: sesión de Laravel + CSRF, sin Sanctum

La SPA y la API se sirven desde **el mismo origen**, así que basta la sesión por cookie del grupo `web`. Sanctum solo añadiría la gestión de tokens y de dominios stateful, que aquí no hace falta.

- Las rutas del panel se cargan desde `routes/panel.php` con el middleware `web` y el prefijo `api/panel` (registrado en `bootstrap/app.php` → `withRouting(then: …)`). El grupo `web` aporta la sesión, la cookie cifrada y la verificación CSRF (`ValidateCsrfToken`/`PreventRequestForgery`, según la versión de Laravel 13).
- Las rutas públicas se cargan desde `routes/publico.php` con el middleware `api` (sin estado y sin CSRF) y el prefijo `api/publico`. Llevan throttling.
- **CSRF en la SPA**: Laravel deja la cookie `XSRF-TOKEN` al servir `app.blade.php`. El cliente fetch (`src/lib/api.ts`) la lee y la envía en la cabecera `X-XSRF-TOKEN` junto con `Accept: application/json`, `X-Requested-With: XMLHttpRequest` y `credentials: 'same-origin'`. Ante un 419, hace `GET /api/panel/auth/yo` (que renueva la cookie) y reintenta una sola vez.
- `config/session.php`: `SESSION_DRIVER=database` (tabla `sessions`, necesaria para revocar sesiones), `SESSION_LIFETIME=120`, `SESSION_SECURE_COOKIE=true` en producción, `same_site=lax`, `http_only=true`.
- `config/auth.php`: el guard `web` usa el proveedor `usuarios` (`driver: eloquent`, `model: App\Persistencia\Usuarios\UsuarioAutenticable`). Se elimina `App\Models\User` y la tabla `users`.
- `config/hashing.php`: `'rehash_on_login' => false`, porque el rehash escribiría por Eloquent saltándose `sp_`. Los hashes usan bcrypt y siempre se generan en PHP: la BD nunca ve una contraseña en claro.
- `UsuarioAutenticable`: `$table='usuario'`, `$primaryKey='id_usuario'`, `$timestamps=false`, `getAuthPasswordName(): 'contrasena_hash'`, `getRememberTokenName(): ''` (no hay "recordarme").
- `bootstrap/app.php`: `redirectGuestsTo('/panel/login')`. Para `api/*`, la respuesta es 401 JSON (`shouldRenderJsonWhen` ya existe).

**Flujo de inicio de sesión** (`AutenticacionServicio::iniciarSesion`). No se usa `Auth::attempt` para poder registrar los casos de denegación:
1. RateLimiter `login`: 5 intentos por minuto por `correo|ip`. Si se supera, 429.
2. Se busca el usuario por correo. Si no existe o el `Hash::check` falla: 422 `CREDENCIALES_INVALIDAS`. Si el usuario existe, se registra `acceso_fallido` en la bitácora.
3. Si el estado es `inactivo`: 403 `CUENTA_INACTIVA` y bitácora `denegado`.
4. `Auth::login($modelo)`, `session()->regenerate()`, bitácora `inicio_sesion` (con IP).
5. Respuesta `{usuario}` con `debe_cambiar_contrasena`.

**Cierre de sesión**: `Auth::logout()`, `invalidate()`, `regenerateToken()` y bitácora `cierre_sesion`.

### 3.2 Middleware

| Alias | Clase | Comportamiento |
|---|---|---|
| `auth` | Laravel | 401 si no hay sesión. |
| `activo` | `UsuarioActivo` | Relee `usuario.estado` en cada petición. Si está `inactivo`: logout + 401 `SESION_REVOCADA`. Es la defensa adicional a la revocación por borrado de sesiones. |
| `cambio_contrasena` | `ExigirCambioContrasena` | Si `debe_cambiar_contrasena = true`, responde 403 `CAMBIO_CONTRASENA_REQUERIDO` en todas las rutas salvo `auth/yo`, `auth/logout` y `auth/cambiar-contrasena`. |
| `rol:Editor,Revisor` | `VerificarRol` | 403 `ROL_NO_AUTORIZADO` si el rol no está en la lista. |

Grupo de rutas autenticadas: `['auth', 'activo', 'cambio_contrasena']`.

### 3.3 Matriz de permisos

E = Editor (incluye a la Secretaría), R = Revisor (Director), A = Administrador. El Revisor tiene los permisos del Editor **más** la revisión ("que además aprueba", P5), pero nunca puede aprobar lo que él mismo editó.

| Acción | E | R | A |
|---|:-:|:-:|:-:|
| Iniciar/cerrar sesión, cambiar su contraseña, recuperar acceso | ✔ | ✔ | ✔ |
| Ver dashboard | ✔ | ✔ | ✔ (KPIs de cuentas) |
| Crear/editar/enviar a revisión/solicitar baja: publicaciones, docentes, planes, cursos, documentos, campañas | ✔ | ✔ | ✘ |
| Gestionar departamentos | ✔ | ✔ | ✘ |
| Decidir revisión (aprobar/observar/descartar), bandeja de revisión | ✘ | ✔ (≠ editor) | ✘ |
| Establecer el plan predeterminado | ✘ | ✔ | ✘ |
| Ver y atender consultas de contacto | ✔ | ✔ | ✘ |
| Ver estadísticas de visitas | ✔ | ✔ | ✔ |
| Registrar solicitudes de acceso | ✘ | ✔ | ✔ |
| Autorizar/denegar solicitudes de acceso | ✘ | ✔ | ✘ |
| Ejecutar alta / cambio de rol / baja de usuario (con solicitud autorizada) | ✘ | ✘ | ✔ |
| Editar datos de usuario (nombres, apellidos, cargo) | ✘ | ✘ | ✔ |
| Ver usuarios | ✘ | ✔ (lectura) | ✔ |
| Ver bitácora de accesos | ✘ | ✔ | ✔ |

La matriz se implementa en `Rol::permisos()` (Dominio), en el middleware `rol:` de cada grupo de rutas y, en la BD, con `sp_rev_assert_rol(p_id_usuario, p_roles TEXT[])`, que llaman todas las funciones de escritura.

### 3.4 Ciclo de vida de cuentas (P5)

1. **Solicitud**: el Administrador o el Revisor registra la solicitud en nombre del solicitante, que no tiene cuenta (`solicitante_nombre`, tipo, rol solicitado, motivo; para un alta también `correo_solicitado` [EXTRA]; para un cambio de rol o una baja, `id_usuario_objetivo` [EXTRA]).
2. **Autorización**: el Revisor autoriza o deniega (`id_director_autoriza`, `fecha_resolucion`). Una denegación queda en la bitácora como `denegado`.
3. **Ejecución**: el Administrador ejecuta. Un alta genera una contraseña temporal (`PoliticaContrasena::generarTemporal`), la guarda con hash, crea el usuario con `debe_cambiar_contrasena=true` y envía `CredencialesTemporalesMail` al correo institucional. Se marca `solicitud_acceso.fecha_ejecucion` [EXTRA] para impedir una doble ejecución.
4. **Primer acceso**: el middleware obliga a cambiar la contraseña. `sp_usuario_cambiar_contrasena` pone el flag en `false` y registra `cambio_contrasena`.
5. **Baja = desactivar, nunca eliminar**: `sp_usuario_desactivar` pone `estado='inactivo'`, ejecuta `DELETE FROM sessions WHERE user_id = id` (revocación inmediata), invalida los tokens de recuperación y registra `baja`. No se puede desactivar a uno mismo ni al último Administrador activo.
6. **Recuperación** (sin autorización del Director): `POST auth/recuperar` responde **siempre 202** para no revelar si el correo existe. Si existe un usuario activo, se crea un token (64 hex, en la BD solo su sha256, vigencia `config('portal.minutos_token')=60`, uso único, los anteriores quedan invalidados) y se envía el enlace `{APP_URL}/panel/restablecer?token=…&correo=…`. `POST auth/restablecer` consume el token, fija la nueva contraseña, pone `debe_cambiar=false`, borra las sesiones y registra `recuperacion`.
7. **Arranque**: el primer Administrador y el primer Revisor se crean con `php artisan portal:crear-usuario {correo} {rol} --nombres= --apellidos= --cargo=`. El comando imprime la contraseña temporal una sola vez y llama a `sp_usuario_crear_inicial`.

### 3.6 Bitácora de accesos

`bitacora_acceso.accion` (VARCHAR) acepta los valores del diccionario `alta, cambio_rol, baja, recuperacion, denegado` más [EXTRA] `inicio_sesion, cierre_sesion, acceso_fallido, cambio_contrasena, edicion_datos`. `id_usuario` es el **usuario afectado**; si no existe (alta denegada), se usa el actor. `id_usuario_actor` es quien ejecutó la acción (NULL si fue la consola), `ip` es la IP de la petición y `detalle` es un texto breve como "Solicitud #12 autorizada por Revisor #3".

### 3.7 Modelado de la Secretaria (decidido)

- **Decisión**: la Secretaria **no es un rol nuevo**. Es un `usuario` con `id_rol = Editor` y `cargo = 'Secretaria de Dirección'` [EXTRA columna `cargo`]. El modelo de 3 roles del diccionario se mantiene intacto. El panel muestra "Editor de contenidos · Secretaria de Dirección". El Director es un usuario `Revisor` con `cargo = 'Director de Escuela'`.
- La semilla base crea los roles con estas descripciones: Editor = "Editor de contenidos (p. ej. Secretaría de Dirección): crea y edita, envía a revisión"; Revisor = "Director de Escuela: además aprueba o rechaza"; Administrador = "Gestiona usuarios y roles; no revisa contenido".
- **Impacto en BPMN, para documentar luego**:
  - P1 (AS-IS) no cambia: la Secretaria redacta.
  - P2, P3, P4, P6, P7 y P8: el carril "Editor de contenidos" pasa a llamarse **"Editor de contenidos (Secretaría de Dirección)"**, o bien se añade una anotación de texto "Rol Editor, ejercido por la Secretaría". Así queda explícito que en el TO-BE la Secretaria ejecuta directamente en el backoffice lo que en el AS-IS hacía el Desarrollador.
  - P5: se añade una anotación en "Crear usuario y asignar rol": "La Secretaría se da de alta con rol Editor".
  - Informe: en la entidad `ROL` hay que añadir la nota "Secretaría = Editor" y, en el diccionario, la columna `usuario.cargo` [EXTRA].

Patrón de toda función `sp_<entidad>_decidir`:
```sql
SELECT estado, operacion_pendiente, id_editor, (cambios_pendientes->>'_id_editor')::int
  INTO v_estado, v_op, v_editor, v_editor_cambio
  FROM <tabla> WHERE <pk> = p_id FOR UPDATE;
IF NOT FOUND THEN RAISE EXCEPTION USING ERRCODE='RN404', MESSAGE='Registro no encontrado'; END IF;
PERFORM sp_rev_assert_rol(p_id_revisor, ARRAY['Revisor']);
PERFORM sp_rev_validar_decision(v_editor, v_editor_cambio, p_id_revisor, p_decision, p_observaciones);
v_nuevo := sp_rev_transicion('<entidad>', v_estado::text, v_op, p_decision);
-- efectos específicos (aplicar JSON, pasar el anterior a histórico, etc.)
UPDATE <tabla> SET estado = v_nuevo::<tipo_enum>, id_director_revisa = p_id_revisor,
       fecha_decision = now(), observaciones_revision = p_observaciones,
       operacion_pendiente = NULL, cambios_pendientes = NULL
 WHERE <pk> = p_id;
PERFORM sp_rev_registrar_historial('<entidad>', p_id, p_decision, v_estado::text, v_nuevo, p_id_revisor, p_observaciones);
```

Detección de ciclos (núcleo de `sp_plan_detectar_ciclo`):
```sql
WITH RECURSIVE camino(origen, actual, ruta, ciclo) AS (
  SELECT p.id_curso, p.id_curso_requerido, ARRAY[p.id_curso, p.id_curso_requerido], p.id_curso = p.id_curso_requerido
    FROM prerrequisito p JOIN curso c ON c.id_curso = p.id_curso WHERE c.id_plan = p_id_plan
  UNION ALL
  SELECT c.origen, p.id_curso_requerido, c.ruta || p.id_curso_requerido, p.id_curso_requerido = ANY(c.ruta)
    FROM camino c JOIN prerrequisito p ON p.id_curso = c.actual
   WHERE NOT c.ciclo
)
SELECT string_agg(cu.codigo, ' → ' ORDER BY ord) INTO v_ruta
  FROM (SELECT ruta FROM camino WHERE ciclo LIMIT 1) x,
       unnest(x.ruta) WITH ORDINALITY AS u(id, ord) JOIN curso cu ON cu.id_curso = u.id;
RETURN v_ruta;   -- NULL si no hay ciclo
```

## 5. Contrato de la API REST JSON

### 5.1 Formatos comunes

**Éxito simple**: `200 {"data": {...}}`. **Creación**: `201 {"data": {"id": 12, ...}}`. **Sin cuerpo**: `204`.

**Paginación** (solo en los listados del panel y en `publico/publicaciones`): query `?pagina=1&por_pagina=20` (máximo 100).
```json
{ "data": [ ... ], "meta": { "pagina": 1, "por_pagina": 20, "total": 57, "ultima_pagina": 3 } }
```

**Error**: siempre con este formato. Se implementa en `bootstrap/app.php` con `$exceptions->render(...)` para `ValidationException`, las excepciones de Dominio, `AuthenticationException`, `AuthorizationException`, `ThrottleRequestsException`, `TokenMismatchException` y `NotFoundHttpException` en `api/*`.
```json
{ "error": { "codigo": "VALIDACION", "mensaje": "Revise los campos marcados.", "campos": { "titulo": ["El título es obligatorio."] } } }
```

| HTTP | `codigo` |
|---|---|
| 401 | `NO_AUTENTICADO`, `SESION_REVOCADA` |
| 403 | `ROL_NO_AUTORIZADO`, `CUENTA_INACTIVA`, `CAMBIO_CONTRASENA_REQUERIDO` |
| 404 | `NO_ENCONTRADO`, `SIN_CAMPANA_VIGENTE` |
| 409 | `ESTADO_INVALIDO`, `DUPLICADO` |
| 419 | `CSRF_VENCIDO` |
| 422 | `VALIDACION` (FormRequest), `REGLA_NEGOCIO` (Dominio/SQL, `campos` con el campo si se conoce), `CREDENCIALES_INVALIDAS` |
| 429 | `DEMASIADOS_INTENTOS` |

Los mensajes de validación van en español (`lang/es/validation.php`, que se publica con `php artisan lang:publish` y se traduce).

### 5.4 Archivos subidos

- **Disco**: `public` (`storage/app/public`), expuesto con `php artisan storage:link` en `/storage/...`. En la BD se guarda la **ruta relativa** y la API devuelve la URL absoluta con `Storage::disk('public')->url()`.
- **Rutas**: `docentes/{uuid}.webp`, `publicaciones/{id_publicacion}/{uuid}.webp`, `planes/{id_plan}/{plan|resolucion}-{uuid}.pdf`, `documentos/{uuid}.pdf`.
- **Procesado** (Intervention Image v3, driver GD; requiere `php-gd`):
  - Publicación: `cover(600, 400)` y WebP 82. Se guarda `ancho_px=600` y `alto_px=400`.
  - Docente: `scaleDown(900, 900)` y WebP 82, sin recorte. El encuadre se aplica con CSS `object-position: x% y%`, como hoy hace `fotoPosicion`.
  - Imágenes: se valida el mime real (`fileinfo`) y no solo la extensión.
- **Borrado**: un archivo solo se borra cuando se reemplaza en `borrador`/`no_publicado` y después del commit (`DB::afterCommit`). Los archivos de registros publicados, históricos o pendientes **no se borran nunca**, por trazabilidad.
- **Límites PHP**: `upload_max_filesize=12M`, `post_max_size=14M` (en `docker/php.ini`; en local, el `php.ini` del sistema).
- La ruta comodín se cambia a `^(?!api|up|storage).*$`, para que un archivo inexistente en `/storage` dé 404 y no la SPA.
- **Migración futura a S3/R2**: basta con `FILESYSTEM_DISK_PUBLICO=s3` y configurar el disco `s3` (Cloudflare R2 es compatible con S3). `AlmacenArchivos` usa siempre `Storage::disk(config('filesystems.publico'))`, nunca `'public'` literal, y como en la BD solo hay rutas relativas no hace falta migrar datos, solo copiar los archivos.
- Los PDF en `en_revision` son accesibles si se conoce la URL, pero el UUID no se puede adivinar. Se acepta en esta etapa.

## 7. Integración del sitio público con la API

### 7.1 Patrón

- `src/data/` contiene el **Modelo y el Controlador públicos** de HU6, en el archivo `src/data/ConsultarInformacionController.ts`, que exporta los hooks. Además:
  - `src/data/adaptadores.ts`: transforma el DTO de la API a las **formas que ya consumen los componentes**, para que los componentes cambien lo mínimo.
  - `src/data/useApiConRespaldo.ts`: hook genérico.
- `useApiConRespaldo<T>(clave, fetcher, respaldo: T)` → `useQuery({queryKey: clave, queryFn: fetcher, staleTime: 5*60_000, retry: 1})` y devuelve `{datos: T | undefined, cargando, origen: 'api' | 'respaldo'}`:
  - Mientras carga: `cargando=true`, y la página muestra un esqueleto o el `Loader` con alto reservado.
  - Si hay **error de red o 5xx**: `datos = respaldo` (el contenido estático de `@profile/content/*`), `origen='respaldo'`, y se avisa por `console.warn`.
  - Si hay datos: se usan los datos de la API, **aunque la lista venga vacía**. El contenido estático se migra a la BD con el seeder del paquete B10, así que una lista vacía significa que de verdad está vacía.
- Registro de visitas: `useRegistrarVisita(seccion)` hace `POST /api/publico/visitas` una vez por sesión de navegador y sección (`sessionStorage`, con try/catch), con `fetch(..., {keepalive:true})`. No bloquea nada y los errores se ignoran.

## 10. Despliegue

**Recomendación: Railway con el `Dockerfile` del repositorio, un volumen persistente para `storage/app/public` y Neon como base de datos.**
Railway despliega Docker desde GitHub con HTTPS y **volúmenes persistentes**, así que el diseño de disco local (5.4) funciona tal cual sin migrar todavía a S3/R2. El scheduler corre en el mismo contenedor y el plan Hobby (≈ 5 USD/mes) basta para el tráfico de una escuela. Vercel no ejecuta PHP, y Render (gratuito) tiene disco efímero y se duerme.

- **Variables** (en Railway, nunca en el repositorio): `APP_KEY`, `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=https://<dominio>`, `DB_CONNECTION=pgsql`, `DB_URL` (endpoint **directo** de Neon, no el pooler, porque el servidor es persistente), `DB_SSLMODE=require`, `SESSION_DRIVER=database`, `SESSION_SECURE_COOKIE=true`, `CACHE_STORE=database`, `QUEUE_CONNECTION=sync`, `FILESYSTEM_DISK=local`, `MAIL_MAILER=smtp`, `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM_ADDRESS`, `PORTAL_DOMINIO_CORREO=unitru.edu.pe`, `PORTAL_CORREO_COMISION`, `LOG_CHANNEL=stderr`.
- **Build**: el Dockerfile multi-etapa (assets con Node, vendor con Composer, runtime FrankenPHP).
- **Arranque** (`docker/start.sh`): `php artisan migrate --force`, la caché de config, rutas y vistas, `storage:link`, el scheduler en segundo plano y el servidor.
- **Volumen**: montado en `/app/storage/app/public`.
- **Health check**: `/up`.

```dockerfile
# ---------- 1) Assets (Vite) ----------
FROM node:22-bookworm-slim AS assets
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --ignore-scripts
COPY . .
RUN npm run build

# ---------- 2) Dependencias PHP ----------
FROM composer:2 AS vendor
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --prefer-dist --no-interaction --optimize-autoloader --ignore-platform-reqs

# ---------- 3) Runtime ----------
# composer.json exige php ^8.3; usar la etiqueta php8.5 de FrankenPHP (si no existiera, php8.4).
FROM dunglas/frankenphp:1-php8.5-bookworm
RUN install-php-extensions pdo_pgsql gd intl zip opcache pcntl
COPY docker/php.ini $PHP_INI_DIR/conf.d/zz-portal.ini
WORKDIR /app
COPY . .
COPY --from=vendor /app/vendor ./vendor
COPY --from=assets /app/public/build ./public/build
RUN php artisan package:discover --ansi \
 && chown -R www-data:www-data storage bootstrap/cache
ENV PORT=8080
EXPOSE 8080
CMD ["sh", "docker/start.sh"]
```

```sh
# docker/start.sh
set -e
php artisan migrate --force
php artisan config:cache && php artisan route:cache && php artisan view:cache
php artisan storage:link || true
php artisan schedule:work >> /proc/1/fd/1 2>&1 &
exec frankenphp php-server --root public --listen ":${PORT:-8080}"
```

`docker/php.ini`: `upload_max_filesize=12M`, `post_max_size=14M`, `memory_limit=256M`, `opcache.enable=1`, `date.timezone=America/Lima`.
`.dockerignore`: `node_modules`, `vendor`, `.env*`, `storage/app/public/*`, `storage/logs/*`, `public/build`, `public/storage`, `.git`, `tests`.
